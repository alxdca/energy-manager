# Energy Orchestrator

Home energy dashboard with manual GEN24 battery controls, solar forecasts, learned household consumption forecasts and optional automatic home-battery charging. PostgreSQL stores quarter-hour observations and estimates, plus the latest household model and versioned weather. Household forecasts use the existing `house_forecasts` table. Daily and hourly measured summaries are derived from observations; there is no durable aggregate cache. Household profiles exclude separately metered car charging. Wattpilot monitoring and manual commands are integrated through the shared `energy-controller`; see its README for the local connection.

See the [energy management policy](../../docs/services/energy-orchestrator/ENERGY_POLICY.md) for the installation, tariff calendar, operating constraints, seasonal use cases and proposed planning behavior. The primary optimization goal is minimum grid-import energy during high-tariff periods, subject to operating limits and required car charge; the home-storage model assumes 95% AC–DC–AC round-trip efficiency.

Car SOC uses a direct Tesla Owner API connection for personal accounts, following TeslaMate’s authentication and `charge_state` protocol. Wattpilot state, measured power and manual normal/eco/pause controls are available through `energy-controller`; automatic car planning is available through explicit Mode auto opt-in.

The battery planner combines hourly solar and baseline household consumption. The battery aims for at least **80% SOC at 16:55**, prepared across **23:05–06:55** and **12:05–16:55**, preserving a 5-minute opening buffer and a 5-minute charging cutoff. Enable it explicitly with `AUTOMATION_ENABLED=true`; imports and standalone API instances never start control loops.

The learned household forecast uses recency-weighted historical local-time slots and, with sufficient history, weekday weighting and a learned temperature correction. It currently forecasts **household consumption excluding car charging**, without a separate learned car estimate. It runs in observation mode; battery control continues using its existing configured baseline pending validation of the learned estimates. Missing forecast slots use a labeled recent-average or configured-baseline fallback; missing measurements stay unknown. See [Household consumption estimate](#household-consumption-estimate).

Car morning minimums are **60% on Monday, Thursday, Saturday and Sunday**, and **50% on Tuesday, Wednesday and Friday**. The checkpoint is 06:55 in `Europe/Zurich`, or an earlier specified departure; required grid charging finishes by 06:55. Overnight planning uses the morning's weekday, and a higher explicitly requested target takes precedence. The dashboard shows the next checkpoint's date and target: today's before 06:55, the next calendar morning at and after 06:55. These morning targets are forced only during 23:05–06:55 after explicitly selecting Mode auto for the car. During 12:05–16:55 the only forced car top-up is from below 30% to 30%; a morning override never raises this afternoon floor. At other times, after a target is met, or when SOC cannot be verified, Auto delegates to Wattpilot Eco. Automatic car commitments remain separate from household load and coordinated with the home-battery plan.

From the repository root:

```sh
cp services/energy-orchestrator/.env.example services/energy-orchestrator/.env
docker compose up -d --wait postgres
pnpm dev:energy-orchestrator
```

The service requires `DATABASE_URL`; the example points to the PostgreSQL 17 container in the root `compose.yaml`. Preserve an existing `.env` and add the URL rather than copying over it. PostgreSQL must be available at startup; there is no automatic JSON fallback. Startup creates the current schema in an empty database.

Open `http://127.0.0.1:3002/` or `/dashboard` for the dashboard. Start the energy controller as well (`pnpm dev:all` starts both), or set `ENERGY_CONTROLLER_URL` in this service's `.env` to its HTTP(S) base URL. The default is `http://127.0.0.1:3001`; an empty value disables the controller connection. Monitoring uses status GETs; enabled automation and explicit control actions can send battery commands. Keep the controller's existing device/control configuration appropriate for your installation.

Navigation opens separate pages: **Accueil** (`/`) for energy flows, daily forecast summaries and desktop controls, **Pilotage** (`/pilotage`) for the dedicated control view, **Données** (`/donnees`) for the selected day of recorded and predicted data, including forecasts up to seven days ahead, **Planification** (`/planification`, « Plan » on phones) for planner decisions and battery readiness, **Tarifs** (`/tarifs`) for tariff windows and planning targets, **Apprentissage** (`/apprentissage`) for learning settings and metrics, and **Appareils** (`/appareils`) for connection status. The former `/previsions` and `/historique` URLs redirect to `/donnees` and preserve their query string. Direct links, reloads and browser Back/Forward work normally. Pages share the French header and theme. Live dashboard pages update every ten seconds; Données reads saved history only. Hidden controls and forecasts on mobile Accueil do not poll. Returning to desktop fetches fresh data; late responses from hidden views cannot overwrite resumed readings or restart polling. Controls require fresh state before enabling actions.

The dashboard displays live solar generation, household demand, signed grid import/export and verified home-battery SOC from GEN24. Each dashboard refresh displays the mean of three fresh GEN24 samples whose starts are 1.1 seconds apart. Browser refreshes start every ten seconds without overlap, accounting for the sampling duration; overruns retry after at least one second. Status requests allow twelve seconds, while each raw upstream request retains its three-second timeout. Sequential batches fetch new data through the controller and inverter client, with no completed-response TTL cache; simultaneous dashboard requests share only the pending batch. Grid and battery powers are averaged with their signs before import/export and charge/discharge are split. SOC, solar and house power use arithmetic means. A missing metric in any sample stays unknown; an incomplete or failed batch never appears as a fresh three-sample average. The last successful average is retained only as stale on failure, with its original observation timestamp. Raw safety checks and energy/history collection keep their existing raw readers and five-second cadence. SOC-progress learning and finish-time publication run on the existing five-second background telemetry collector, independently of browser requests and forecast batches. Page reads validate the latest publication; invalid telemetry or a changed command clears it. Missing values remain unknown. Controller observations older than 30 seconds or retained after a failed refresh are explicitly marked stale with their original timestamp. Tesla SOC and Wattpilot state are read independently, with their original timestamps and freshness. The automation status reports the observed running planner separately from tariff-window availability; car planning status is reported separately.

Accueil consolidates readings into one energy-flow card. Solar, grid, battery, car and house connect to a neutral central junction. Particles indicate averaged flow direction only for fresh, nonzero readings; solar averages below 5 W display as 0 W and do not animate; zero, missing, stale and offline readings do not animate. Motion pauses when the page is hidden and waits for refreshed readings on return; reduced-motion preferences disable animation. Powers use W below 1,000 W and kW above, with battery SOC and the car's morning target retained in their nodes. **Maison** adds the current signed flow residual to measured household power. Each averaged power reading is first rounded to whole watts, and all balance and house-adjustment arithmetic uses those integers. For example, 500 W measured consumption with an 88 W residual displays 588 W. Its animation uses the adjusted power. No provisional balance line is displayed. All six initial readings must be known, nonnegative and online to apply the adjustment; otherwise valid measured house power remains displayed. A negative adjusted result is unknown. This is a display convention that assigns the residual, including conversion losses and measurement timing, to Maison. Raw live telemetry includes car loads; archived house observations, daily totals, charts and household learning exclude charging. The combined house-and-car measurement is used only to calculate the house-only counter and is not archived.

## Weather and solar forecast

Forecast and planning estimates share one scheduled writer. A complete initialization runs immediately at service startup (including solar). Thereafter household consumption, battery SOC trajectories, planner previews, afternoon requirements/source allocation update at **:00, :15, :30 and :45** in Zurich. Solar/weather provider reads occur in the **:00** batch; other batches reuse the retained solar model and original `fetchedAt`.

Each scheduled loop refreshes household estimates and their latest model/profile context in one PostgreSQL transaction, then publishes solar and battery estimates with their planning context in another. Once household forecasts have been published, the planning writer never overwrites `house_forecasts` with its configured baseline. An energy quarter becomes immutable as soon as it starts; only later solar and household quarters can be replaced. Passed battery targets stay frozen. Older batches are rejected against saved publication timestamps, including after restart. The third forecast day remains input for tomorrow’s planning. Observation and provenance collectors persist measured data independently and cannot publish forecasts.

Données reads the canonical quarter-hour rows through a consistent database snapshot and aggregates the selected day into hours for its chart. It does not read weather, calculate consumption, project battery SOC or archive estimates. Forecast values and totals stay fixed between committed batches: API and browser clocks do not prorate them. A failed publication keeps the previous committed batch; before the first commit, estimates remain unavailable. Missing history stays unknown.

Forecast card footers show **Bilan : HH:mm · Solaire : HH:mm**, using the committed batch’s `estimates.calculatedAt` and the provider’s original `fetchedAt`. Manual changes immediately invalidate incompatible battery predictions and finish-time estimates; after restart or a control change, SOC predictions wait for a valid scheduled batch. Safety checks, charging-window cutoffs, lease renewals, measured SOC/powers and observed history retain their independent timing.

Accueil shows **Aujourd’hui** and **Demain** forecast summaries with production, consumption, weather and temperatures. Both cards align production, household consumption and planned car charging in three columns. Today also shows observations above forecasts. Forecast totals sum all saved `solar_forecasts`, `house_forecasts` and `car_forecasts` rows for that Zurich calendar day, including past quarters and days with gaps. Empty channels remain unknown; saved zeroes remain zero. The `dailyTotals` response field supplies these sums independently of forecast coverage, weather availability and household fallback calculations. Observed daily energy remains separate from forecast energy and sums the day’s recorded readings. Appareils reports the weather connection separately from the battery planner. `GET /api/forecast` retains tomorrow’s contract; `GET /api/forecast/today` returns the same fields for today. Both are independent of live GEN24 reads, so an unavailable weather provider does not delay telemetry.

Données adds a responsive hourly chart above its chronological table for the selected date. Visible energy uses whole Wh at the formatting boundary; API values, storage and planning remain in kWh, and battery SOC remains a percentage. Predicted solar uses pale amber bars with narrower measured DC bars overlaid; predicted household consumption is dashed and measured consumption is a solid line with gaps. Battery measurements use a solid purple line and saved predictions use a dashed purple line against a 0–100% right axis. Missing values remain gaps rather than being reconstructed. The chart and table reuse the same historical-day response, adding no dependency, live telemetry read or browser poll. Actual Zurich days contain 23, 24 or 25 hourly slots.

The same two forecast responses now include `measurements`, a full Zurich-day calendar of hourly GEN24 solar/household energy integrals and per-channel coverage. No additional reader, telemetry poll or device command is created. Measurements remain available during a weather-provider outage. Unknown and future hours are `null`, including after clock rollback; real measured zero is retained. Partial/current-hour measurements are observed subtotals, never extrapolated to a complete hour. Table cells show plain observed subtotals without partial-duration labels; SVG titles retain the covered duration, and the first hourly measurement time is displayed. Measured consumption is not connected across missing hours.

Measured solar is **GEN24 PV DC**, while the production forecast includes a system-loss factor. Measured household consumption and learned forecasts exclude verified Wattpilot charging; the page labels household inclusion and omits **DC** from solar labels, legends and tooltips. These overlays are descriptive comparisons, not automatic calibration or proof that forecasts and measurements share an AC/car-free boundary.

PostgreSQL retains finalized domain observations without an age cutoff; a database advisory lock enforces one history writer. Startup initializes an empty database with the current schema (version 11). There are no automatic migrations, legacy readers or JSON importers.

The API adds `hourly` solar slots with ISO UTC `start`/`end`, unrounded `estimatedProductionKwh` and optional `temperatureC`. Complete roof irradiance is required; unavailable solar or horizontal daily-only mode returns `hourly: null`, never fabricated night/day values. The east-facing request also fetches hourly temperatures; a missing temperature does not turn missing weather into zero or discard valid production.

The legacy controller `consumption` field keeps aligned `hourly` slots and `hourlyMethod: baseline_only`. The constant baseline applies to each actual elapsed hour. The separate `householdForecast` field contains the learned observation-mode profile; car-separated measured history remains future work.

Set `FORECAST_LATITUDE`, `FORECAST_LONGITUDE` and optionally `FORECAST_LOCATION_NAME` in this service's `.env`. Both coordinates are required; leaving both blank disables solar/weather forecasting while retaining the configured consumption estimate. Configure the location for your own installation. Restart the orchestrator after changing environment settings.

The configured installation has an east-west roof with **15° tilt** and roughly equal capacity on each side: **4.25 kWp east and 4.25 kWp west**. The owner reports no significant shading. Set `FORECAST_PANEL_TILT_DEG=15` and `FORECAST_EAST_FRACTION=0.5`. Tilt accepts 0–90 degrees; the east fraction accepts 0–1 and defaults to 0.5 when tilt is configured. It is the share of total installed power, not an additional capacity.

The local installation selects `FORECAST_WEATHER_MODEL=meteoswiss_icon_ch2`: [ICON-CH2 through Open-Meteo](https://open-meteo.com/en/docs/meteoswiss-api), approximately 2 km with underlying hourly weather output and a five-day horizon. Open-Meteo interpolates that model to the requested 15-minute irradiance steps; these are independently calculated quarter-hour energy targets, not native 15-minute weather-model output. Other installations default to `best_match`; only these two identifiers are accepted. Best Match currently selects other regional models in Central Europe rather than ICON-CH2. The selected identifier is returned as `weatherModel`. Regional selection targets the configured installation; no measured comparison yet proves it improves forecast error. Today through two days ahead retain the configured model. From three days ahead onward, forecasts explicitly use `best_match` so complete calendar days remain available beyond CH2’s 120-hour horizon; the actual identifier is returned as `weatherModel`. A failed near-term regional request retains its original model and stale-data behavior. Household temperature forecasts use `best_match` through the longer horizon.

With tilt configured, three concurrent bounded requests fetch daily Zurich weather and [15-minute tilted irradiance](https://open-meteo.com/en/docs) for east azimuth −90° and west +90° (south is 0°). Irradiance requests use `minutely_15=global_tilted_irradiance`, GMT Unix timestamps and explicit `start_minutely_15`/`end_minutely_15` bounds. Each W/m² value is the **preceding-15-minute mean**: request endpoints from local midnight plus 15 minutes through and including the following midnight. Require exactly 92, 96 or 100 consecutive endpoints for the actual Zurich calendar day, with complete finite data on both roof faces. `productionPeriodStart`/`productionPeriodEnd` remain ISO UTC instants. Missing samples are unavailable, never an invented zero.

For each quarter, calculate `0.25 × array kWp × PV system factor × (east fraction × east irradiance W/m² + west fraction × west irradiance W/m²) ÷ 1,000`. Each target uses its own provider irradiance value, so four quarters of an hour can differ. Preserve unrounded energy in `quarterHourly`, derive each `hourly` chart value by summing four quarters, and round only the displayed daily total once to one decimal kWh. The dashboard does not claim measured precision. Both complete roof series must be valid; a partial result is unavailable rather than silently using one face. Battery planning, SOC projections and high-tariff calculations consume the validated quarter-hour profile; the existing hourly chart/table remains a display aggregate.

Leaving tilt blank retains the coarse horizontal model: daily `MJ/m² ÷ 3.6 × array kWp × PV system factor`, with null production-period metadata and no sub-day solar profile; it does not invent quarter-hour forecasts. `FORECAST_SOLAR_CAPACITY_KW` defaults to 8.5 and `FORECAST_PERFORMANCE_RATIO` to 0.85; the latter is separate from battery round-trip efficiency. No significant shading is reported, but snow, temperature-dependent panel efficiency, local horizon effects and measured-production calibration remain unmodeled. Adding a generic thermal coefficient to an all-inclusive system factor risks counting temperature losses twice. Observed PV DC production is now recorded as daily power integrals, but no verified solar AC daily counter or automatic calibration exists. DC observations must not be treated as equivalent to the forecast’s loss-adjusted output without reconciling measurement boundaries; no statistical confidence interval is claimed.

The backend caches each day’s forecast independently for one hour, coalesces concurrent requests and limits the complete provider operation to four seconds. Scheduled provider failures with a usable retained profile wait until the next full-hour batch; missing days retry at the next quarter-hour; the underlying reader retains a five-minute failed-attempt backoff for standalone callers. After a failed refresh, the last complete successful forecast remains usable for its original target date without a one-hour or six-hour expiry. It stays labeled `stale`, retaining its original `fetchedAt` and the refresh error. At Zurich midnight, scheduled batches can reuse the previously prefetched forecast for that exact date; they never relabel another day's data. The live provider cache remains in memory and retains source/weather metadata. On a restart-time request failure, the estimate service can also reuse a complete saved forecast for that same future calendar day and installation parameters. PostgreSQL stores canonical quarter-hour solar values plus the committed batch’s weather/profile context and original retrieval timestamp. Saved started quarters preserve internal planning history after restart; the provider cache starts independently, and Données can read the previous committed batch. HTTP failures report their status code, invalid JSON is identified, and timeouts report the four-second limit without exposing provider response bodies. Exact UTC irradiance integration does not change the provider's fixed-offset daily weather aggregates or coarse horizontal fallback. In live responses, `fetchedAt` is retrieval time, not model issuance.

The browser checks each visible card’s cached endpoint every ten seconds from the previous request start, without overlapping reads. Failures and eight-second timeouts are independent by card; hiding the document or the desktop-only home cards cancels both reads and ignores late results. Appareils reads only tomorrow for its weather state. Missing radiation is unknown, not zero. Provider and [Open-Meteo licence](https://open-meteo.com/en/licence) references remain documented here; forecast cards keep concise status and measurement-source labels. Its free API is suitable for this [personal, non-commercial use](https://open-meteo.com/en/terms).

Données plots **Batterie relevée** and **Batterie prévue** from the saved history on a separate purple **0–100% right axis**; energy remains on the left Wh axis. Hourly values use the last valid observation or saved target inside each hour, without averaging or carrying values across gaps. The predictions are provisional trajectories, not guaranteed charge schedules or command records. Collection begins with implementation; previous SOC history is not reconstructed. Observations remain available through weather outages, and battery-only data does not invent energy values. SOC history is checkpointed by the same background collector in PostgreSQL. Database history has no age-based deletion policy; bounded working caches do not limit durable history. Graceful shutdown flushes pending history before closing the database.

Battery SOC predictions are persisted in `energy_history.battery_forecasts`. Each forecast transaction replaces future **15-minute UTC targets** as `{ at, socPercent }` and preserves elapsed targets. Current measured anchors are not stored as predictions. Données reads these rows for comparison with actual SOC even when live automatic predictions are unavailable. Forecast publication is independent of browser activity. There is no separate prediction cache, reader-side capture, observation-flush writer or age-based deletion. Batch metadata preserves the publication timestamp so older batches are rejected across restart; individual estimate tables retain their timestamp-and-value format. Missing historical predictions remain unknown.

## Quarter-hour solar and house estimates

Public forecast responses include `forecastPeriod` with the Zurich calendar `start` and `end`, plus `from` at the start of the clock hour containing the committed batch cutoff. The full current hour is included, without duration proration or partial-hour display. Hourly and summary totals sum the same saved quarters used by Données. GET requests and browser rendering never adjust these estimates using the request clock. A daily-only solar source cannot supply canonical quarter rows and is unavailable in Données. Measured observations remain independent. Planification still hides session-specific starting-SOC, afternoon SOC and completion predictions after their target times pass.

Solar production estimates depend on Open-Meteo forecasts and fixed installation parameters (array power, orientation, tilt and performance ratio). Measured inverter production does not recalibrate them. The source reader refreshes at startup and each full hour, producing a complete profile of independently calculated **15-minute energy targets** from that batch. `energy_history.solar_forecasts` stores each `quarterHourly` value directly; it no longer divides a new hourly solar estimate into four equal rows. At intermediate quarter-hours, planning reuses the same per-target solar profile without another provider request. Hourly chart values are sums of the four underlying targets. Sub-day forecasts use the current `quarterHourly` contract; missing or malformed quarter profiles are unavailable.

At startup and each aligned quarter-hour update, `energy_history.house_forecasts` stores the learned household consumption excluding car charging, per ongoing/future 15-minute interval. Missing learned slots use the labeled recent-average or configured-baseline fallback. Every started interval retains its recorded value and only later intervals can change; starting partway through a quarter fills it only when no saved estimate exists. House, car and solar energy forecasts retain exactly `interval_start` and `energy_kwh`; house forecasts always exclude car charging. The household publication timestamp and latest model/source context live in `metadata.household_forecast_v1`, committed with the rows; numerical forecast values and totals are not duplicated in metadata. Forecast APIs and Données read the same canonical values. The battery planner retains its separate car-free configured baseline and explicit car allocations; its baseline is reconstructed from saved configuration on restart rather than restored from household-total rows. Without the household publisher, standalone planning batches can still persist baseline estimates.

A normal Zurich day contains 96 quarter-hours; clock-change days contain 92 or 100. Both archives survive restart without automatic deletion. History capture runs without an open browser or enabled battery automation. Live forecast responses still expose their batch and solar refresh times; removing archived generation timestamps does not remove these live freshness indicators.

Completed energy intervals and elapsed battery targets stay frozen across updates and restarts. Future and ongoing estimates can change only when the forecast loop commits another batch. Données exposes the saved rows across the selected day. Startup restores saved consumption and solar intervals for internal planning; it does not backfill missing historical estimates. Live charging ETAs describe the current session and do not replace historical energy or SOC predictions.

## Tesla state of charge

Open **Appareils → Connexion Tesla** and paste an **Owner API refresh token** obtained with one of the tools listed in [TeslaMate’s token guide](https://docs.teslamate.org/docs/installation/tokens). Click **Connecter**. No TeslaMate installation, Tesla password, access-token paste or new dependency is required. Do not send the token through chat or commit it to Git. If the account contains several cars, set `TESLA_VIN` in this service’s `.env` and restart before connecting.

The account is connected directly to `auth.tesla.com` and `owner-api.teslamotors.com`, using the same `ownerapi` refresh grant as [TeslaMate](https://github.com/teslamate-org/teslamate/blob/main/elixir/lib/tesla_api/auth/refresh.ex). Token exchanges use native Node HTTP/2 over verified TLS 1.3, matching [TeslaMate’s transport correction](https://github.com/teslamate-org/teslamate/pull/5406). HTTP/1.1 token exchanges can succeed yet issue tokens that receive Owner API 403 responses. Valid saved tokens are reused until normal expiry or an authorization refresh is required. Telemetry GET requests continue to use fetch. This is the **unofficial Owner API for personal accounts**; availability can change. Fleet/Business and China accounts and Fleet tokens are not supported by this adapter. TeslaMate documents the [difference between Owner and Fleet access](https://docs.teslamate.org/docs/configuration/api). Initial token generation deliberately follows TeslaMate’s external-token approach, rather than collecting Tesla passwords in the dashboard.

The background reader starts with the server and works without an open browser. It selects the vehicle from `/api/1/products`, checks its state, then requests only `vehicle_data?endpoints=charge_state` while online. Successful reads are spaced one minute apart; asleep/offline vehicles and failures back off for five minutes. HTTP 429 honors a longer `Retry-After`; `EXCEEDED_LIMIT` backs off for fifteen minutes. An expired access token is renewed automatically, with one renewal/retry on HTTP 401; rejected refresh tokens require reconnection. Requests have a ten-second deadline and never follow redirects with credentials. Passive polling sends no wake-up or charging command. Explicitly enabled car Auto may use the bounded wake-only path described below; actual charging remains owned by the Wattpilot controller. Polling an online vehicle can still delay sleep; this adapter does not reproduce TeslaMate’s full sleep-management state machine.

Set `CAR_NAME` in this service’s `.env` to the car name displayed throughout the dashboard (for example, `CAR_NAME=Tesla Model 3`). An unset or blank value displays `Voiture`. Restart the orchestrator after changing it.

Accueil shows the car’s measured percentage and charging/connection state. Appareils shows the vehicle SOC and connection errors without a refresh date/time; freshness still determines the state label. Measurements older than ten minutes are marked old; asleep/offline/errors retain only the last known dated SOC and clear current charging state. Without a first valid vehicle observation, SOC stays unknown. Car power comes independently from Wattpilot. Fresh measured car power is subtracted once from the displayed Maison balance; raw household telemetry still includes car charging. New history and learned forecasts exclude it using paired AC energy counters. The home-battery planner includes the active automatic car schedule through a separate car-load channel. The last valid car SOC, its original observation time, charge limit and vehicle identity are saved with the Tesla connection and restored after restart as an old measurement, with no current charging state. Planification also displays this dated last-known SOC while the car is asleep, offline or unavailable; charging predictions and automation still require fresh observations. The cache is cleared on reconnection, disconnection or discovery of a different vehicle, and ignored if invalid or incompatible with TESLA_VIN. It is not added to the home-battery PostgreSQL history.

Tokens stay server-side in `data/tesla-tokens.json` (or `TESLA_TOKENS_PATH`). The file is **plaintext with permissions `0600`**, atomically replaced after token rotation and each valid charge observation, in the existing Git-ignored data directory. Protect this directory and its backups; run one orchestrator per token file. If a custom path is used, exclude it from Git as well. Dashboard responses never return tokens, and the password field is cleared upon submission. **Déconnecter** waits for any current read, deletes this server’s token file and clears its cached car data; it does not revoke Tesla’s account authorization. Keep the dashboard on a trusted local network or behind authenticated HTTPS/VPN, as with the existing battery-control endpoints.

`GET /api/tesla` returns the cached public car telemetry without contacting Tesla. `/api/status` and `/api/planner` include the same `car` object. `POST /api/tesla/connect` accepts only `{ "refreshToken": "…" }`; `POST /api/tesla/disconnect` accepts `{}`. Both require JSON and reject cross-origin browser requests. Importing the API module alone starts no background task.

## Recorded observations

Observation acquisition reads the GEN24 every **30 seconds** on wall-clock boundaries. These readings are candidates held only in RAM. At each UTC **15-minute target**, retain the latest valid sample strictly before the target. A reading exactly at the target belongs to the next target. Never average samples, substitute an expected bucket timestamp, repeat an old sample into a missed window, or persist an unfinished candidate on shutdown.

The three active observation tables contain exactly two columns:

| Table | `observed_at` | `value` |
| --- | --- | --- |
| `battery_observations` | Actual selected battery component timestamp | SOC, % |
| `solar_observations` | Actual selected PV counter timestamp | Quarter energy, Wh |
| `house_observations` | Latest input timestamp of the selected household counter snapshot | Quarter energy, Wh |

SOC is the selected raw value. Energy is the difference between consecutive selected cumulative counters, without power integration or averaging. The installed GEN24 exposes PV-string DC energy counters and AC inverter production/consumption counters through its read-only component endpoint. Inverter component counters are converted from Ws to Wh; Smart Meter absolute counters already use Wh. Household cumulative energy is net inverter AC energy plus net grid energy: `AC produced − AC consumed + grid imported − grid exported`. Grid import alone is not household consumption, and AC inverter production alone is not PV DC production. Device identities, native counter totals, source timestamps and primary-grid-meter location are validated.

The first selected energy reading establishes a baseline and produces no invented energy row. Counter resets, changed source/native-counter identities, negative deltas, or missing consecutive targets establish a new baseline and leave that quarter unknown. Native component resets are checked separately so a reset of a subtractive grid/export counter cannot create a false positive household delta. Only finalized counter baselines and the finalized-target watermark are checkpointed, atomically with the observation rows. Intermediate 30-second candidates never enter tables or metadata. Finalized pending rows stay in memory during transient database failures and retry idempotently; unfinished candidates are lost on process failure by design.

Battery provenance and existing control/safety accounting retain their independent **five-second** telemetry feed and continuity rules. The slower observation sampler does not weaken the safety limits or create a thirty-second gap in solar-origin accounting. Provenance checkpoints are independent control state, not an observation-sample archive.

The history API exposes new energy observations as actual `{ at, value }` points under `observations.solar` and `observations.household`; their values are Wh. Summaries use `method: recorded_energy` and sum whole values by their real timestamps. Hour/day aggregation does not proportionally split a sampled energy difference at a calendar boundary or invent measured coverage. Données displays Wh; compatible energy-summary fields remain kWh at the API display boundary. SOC uses its real observation time and is compared with the prediction for the next 15-minute target. Future forecast views still exclude past predictions.

Missing observations remain unknown; there is no automatic observation-history deletion policy.

## Forecasts in history

Données displays production, household consumption and battery forecasts through its main daily chart and quarter-hour/hourly table. The date picker and next-day arrow stop at **today + seven Zurich calendar days**. Direct links beyond that date are normalized to the last permitted day; `GET /api/history/day` rejects later dates with HTTP 400. Past history stays accessible. There is no separate seven-day forecast card or weekly summary endpoint.

Scheduled batches save today, seven future days and an additional internal planning lookahead day. Usable solar profiles refresh hourly; missing solar days are retried at the next quarter-hour batch while valid days retain their original profiles. Battery and consumption estimates update every quarter-hour. The battery simulation carries measured SOC continuously through the end of the seventh future day, using the extra day to fund the final 23:05 night decision. Actual gaps stop the trajectory and remain unknown. If individual solar requests fail after restart, complete saved forecasts for the same dates and installation parameters are restored as stale instead of erasing usable future days. A failed restore read aborts publication and preserves the previous batch.

Battery forecasts remain available with automation disabled: passive operation models solar, consumption, losses and reserve without scheduled grid charging. Confirmed manual charging keeps its session assumptions. Automatic charging limited below 6 kW uses the confirmed power until the next planning evaluation. Forecasts do not enable automation or issue commands. The history response includes the projection status/reason and solar source status, and the chart explains unavailable or partial forecasts. ## Household consumption estimate

The household stage of the [consumption forecast strategy](../../docs/CONSUMPTION_FORCAST.md) is implemented in observation mode. `household-model.ts` uses up to 84 prior Zurich days plus today's finalized readings available at the training cutoff, a 14-day recency half-life and a ×4 same-weekday bonus once at least 14 days have complete sampling and a slot has four matching weekdays. Today's partial day contributes only to observed time slots; missing or later slots are not extrapolated and a partial day does not count as complete sampling. It fits no fixed baseline or assumed heating quantity. Household energy is the recorded counter delta in Wh divided by 1,000, assigned whole to the quarter containing its actual timestamp. This is explicitly a nominal-quarter approximation, not proof of 900 seconds of coverage. Duplicates and invalid observations are excluded and valid zeros retained. Repeated autumn wall-clock slots contribute one mean per historical day; forecast days retain their actual 92/96/100 UTC intervals.

**Forecast fallback:** missing prediction slots are filled after learning, in this order: an available learned value, then the average power of eligible readings in the last `FORECAST_FALLBACK_WINDOW_HOURS` (24 hours by default; configurable from 1 to 168), then `FORECAST_BASE_LOAD_W` (1,000 W by default). The average requires at least four distinct finalized quarters and a reading within the last hour. It divides measured kWh by the duration of eligible intervals, not by the full window with missing quarters counted as zero. Observed interval durations are used when valid metadata exists; legacy deltas use an explicit nominal-quarter approximation. Ambiguous duplicates, invalid or future readings and intervals still in progress are excluded. Recent averages refresh every quarter, including across midnight, without retraining. Valid learned values and zeros are preserved. This fallback is a requested extension of the strategy's original unavailable-on-missing behavior; it is never used to train profiles or weather coefficients.

Fallback forecasts expose `status: fallback`, per-slot `source` and a `fallback` summary with window, sample count, sampled hours, average/baseline power and affected slot count. Mixed profiles retain their learned slots. Hourly and daily totals are sums of these predictions, including 23-/25-hour days. Home cards, historical table notes and chart tooltips identify fallback sources. Actual measurement gaps and historical forecast versions remain untouched: only versions issued before a slot began appear in its history. A failed training run remains an error, while a labeled baseline forecast supplies future estimates if it can be saved.

The existing estimate scheduler invokes the household service at startup and at **:00/:15/:30/:45**. A saved model is reused throughout its Zurich training day, including after restart. The first scheduled run on a new local day finalizes measurements and trains again; models expire at the next Zurich midnight. Each training run freezes its cutoff after measurement finalization and uses that same instant for reading completed quarters, selecting the Zurich date, and recording `trainedAt`. Training metadata includes today in `training.to`. The fixed-quarter model uses version `household-profile-v3-car-free`; previous models rebuild on the next refresh. Training builds the profiles as well as the weather coefficients; weather fitting still requires eligible complete days. Ordinary quarter-hour updates perform lookup and weather adjustment, not full training. Predictions cover today, seven future days and one planning lookahead day; page GETs only read saved results.

Open-Meteo hourly temperature is read independently of panel geometry. Forecast temperatures refresh hourly, and ERA5-Land reanalysis is retrieved daily with a conservative six-day lag. Weather versions retain source, model, coordinates, valid times, fetch/availability time and hourly resolution. Reanalysis availability is conservatively the retrieval time. Household learning reads `house_observations` directly: each row represents the fixed 15-minute UTC quarter containing its actual `observed_at` timestamp, without changing that timestamp or the stored Wh value. Weather integration uses those nominal quarter boundaries, and recent-average fallback counts 0.25 hours per observed quarter. Only quarters completed by the cutoff are eligible; missing or duplicate quarters stay unknown. Calibration requires complete days and complete hourly weather coverage, with no additional interval table or endpoint-alignment requirement. Temperature is linearly interpolated without extrapolation. This uses nominal quarter alignment rather than reconstructing exact counter-sampling durations.

Weather calibration needs at least 28 eligible complete days plus separate seven-day selection and seven-day final diagnostic holdouts (42 days total), seven days on each side of a candidate threshold and at least 3 °C contrast. Weighted regression fits weekday intercepts and a nonnegative shared cold sensitivity, testing thresholds drawn from observed temperatures. Full-profile validation requires ≥10% lower daily MAE without >5% degradation in quarter-hour or tariff-window MAE, and coefficient stability across training windows. This uses **realized historical weather for diagnostics**, not a claim of operational forecast accuracy. Historical heating is removed before forecast heating is added. Missing/stale weather, insufficient diversity, failed validation or extrapolation falls back to the learned uncorrected profile. Uncertainty remains uncalibrated; battery control is not automatically promoted.

**Manual training:** on **Apprentissage** (`/apprentissage`), select **Relancer l’apprentissage complet**. It reloads history including today's finalized readings through that run's cutoff, rebuilds profiles and weather calibration, then immediately saves forecasts for the full horizon. Concurrent manual/scheduled requests share a serialized job. The page shows training progress, last/next daily cycle, model version, eligible-day and observation counts, weather calibration and today’s saved forecast coverage (learned versus fallback slots). Active settings are read-only: daily training, history window, half-life, slot resolution, weekday weighting and the actual configured fallback window/power. Configure fallback values with `FORECAST_FALLBACK_WINDOW_HOURS` and `FORECAST_BASE_LOAD_W`. Missing metrics remain unknown; coverage is not an accuracy score. Status and saved forecasts refresh every 30 seconds (every two seconds during training), pause while hidden and never trigger training on GET. API equivalents:

```sh

curl http://127.0.0.1:3002/api/household/training
```

The forecast APIs expose `householdForecast` separately from the controller's legacy `consumption`, with 15-minute `slots`, hourly sums, scope, issuance/model IDs, training coverage, weather status and explicit fallback reasons. The home forecast uses the learned total. Données reads `house_forecasts`; `householdPredictions` and `energyEstimates` expose the same rows. Started quarters preserve their values, future quarters are replaced by the latest forecast, and missing past predictions are never backfilled. Full forecast revision history is no longer collected. Only the latest trained model is stored under the `household_model_v1` metadata key, including its ID, training time, profiles, calibration and summary metrics. Solar refreshes and the existing quarter-hour irradiance values are unchanged. The model adds no ML dependency, Python process, AI API or separate car estimate.

The heat-pump range, enablement flag, reference temperature and heating threshold settings have been removed; inherited values are ignored. Weather availability and temperature do not change consumption estimates. Restart the orchestrator after configuration changes.

This controller estimate is provisional. Heating, hot water and appliance peaks beyond the baseline are not modeled in it; car charging and battery-charging energy are excluded. The separate learned household forecast above includes the measured site's habits and learns weather effects when supported. Existing archived controller estimates retain their original values.

## Automatic battery charging

Set `AUTOMATION_ENABLED=true` after configuring controller write opt-in and a power ceiling of at least 6 kW. `AUTOMATION_SOC_CAPACITY_KWH=60` encodes the owner-confirmed meaning of reported 0–100% SOC. `AUTOMATION_RESERVE_SOC_PERCENT=5` is the owner-confirmed minimum reserve. Both planning and displayed availability protect at least 5%, or a higher configured/verified inverter reserve. Values below 5% cannot lower this floor. Unknown reserve, stale measurements, unavailable complete hourly forecasts or insufficient controller capabilities block new automatic commands.

The shared estimate batch initializes immediately and then runs on each quarter hour, independently of browsers. It supplies current inputs and awaits the runner before publishing predictions. The runner also maintains control at opening buffers, cutoffs and manual transitions without initiating new forecast/model batches:

- **Afternoon goal:** reach at least **80% SOC at 16:55**, configured with `AUTOMATION_AFTERNOON_TARGET_SOC_PERCENT=80`. If the evening's chronological consumption and solar require more energy above the protected reserve and forecast-error cushion, raise the desired goal. This goal applies at 16:55 itself; do not add another bridge allowance merely to preserve 80% at 17:00. The existing 16:55–23:00 evening coverage calculation still protects the bridge and high-tariff needs.
- **Night:** forecast the path through the morning and daytime to 16:55. Count only useful solar after household loads, in time order and within battery charge/discharge power and capacity limits. Favor overnight charging for the remaining gap after that solar contribution, while retaining enough energy for 06:55–12:00 and its forecast-error cushion. Later solar cannot repair an earlier morning deficit. Before midnight use tomorrow's forecasts; after midnight use today's.
- **Afternoon:** reassess the same 16:55 goal using updated forecasts and current SOC; finish any shortfall left by night charging limits, insufficient time, lower solar or higher consumption. The target for the current charge command can differ from the final afternoon goal.
- **Commands:** charge at up to **6 kW** until the calculated intermediate target or finite expiry. Reduce the home-battery setpoint to the remaining site headroom after household demand and required Tesla charging; zero available charging power uses an owned hold. Once prepared, preserve battery energy with a controller-owned hold until 06:55 or 16:55, then return to normal inverter behavior. The battery charging command does not force discharge or change the car's current.

The usable forecast-error cushion is `max(1 kWh, 5% × next high-tariff battery energy needs)`. Configure `AUTOMATION_ENERGY_BUFFER_PERCENT=5` and `AUTOMATION_ENERGY_BUFFER_MIN_KWH=1`; these replace the fixed-kWh setting. The percentage uses the next 07:00–12:00 or 17:00–23:00 interval's aggregate net house demand after forecast solar, converted to stored energy with the discharge efficiency. Its percentage basis excludes the protected reserve, the five-minute cheap-tariff bridge and periods outside the next high-tariff interval; the bridge itself remains part of the chronological energy target. For 10.1 kWh of battery demand the margin is 1 kWh; for 30 kWh it is 1.5 kWh. Morning coverage and evening coverage retain their own cushion; the 80% SOC floor does not receive another cushion on top when it already covers the evening requirement. Desired goals and feasible command targets remain distinct, and unmet energy is reported after SOC/time caps. Percentages must be finite 0–100 and the minimum finite 0–capacity; setting both to zero explicitly disables the cushion. The calculated margin remains available in `automation.plan.energyBufferKwh`. Available energy excludes only the protected reserve, since the cushion remains usable. This cushion reduces forecast risk but cannot guarantee coverage.

95% round-trip efficiency is split as √0.95 per conversion leg. Chronological calculations respect reserve, controller maximum SOC, available charge time, storage capacity and forecast charge/discharge power constraints. `unmetKwh` reports the overall stored-energy shortfall against planning goals, including the preferred afternoon SOC and forecast cushion. `nextHighTariffUnmetKwh` separately reports only the consumption that battery plus chronological forecast solar cannot cover during the next high tariff: 07:00–12:00 for night planning, 17:00–23:00 for afternoon planning. It respects reserve, feasible charging, conversion losses, storage and power limits, and solar timing. The preceding five-minute bridge affects available SOC but is not itself counted as missed high-tariff demand. **Couverture limitée** and its displayed missing kWh use only this next-period deficit; a missed SOC goal, cushion or later-period requirement alone does not trigger the warning. Unknown coverage remains `null`. `nextHighTariffChargeNeededKwh` evaluates that same next period without scheduled grid charging, retaining the current stored energy, useful net solar, reserve, conversion losses and physical limits. The UI uses **Charge nécessaire** only for a positive deficit in this scenario, **Charge de réserve** when the next high tariff is already covered and charging instead prepares the preferred SOC or forecast cushion, and **Charge prévue** when the need is unknown (including older saved plans without this field). This display distinction does not change the 80% goal or charging commands; **Couverture limitée** still reports a positive deficit after feasible charging. Household estimates are still synthetic, rather than learned from yesterday's hourly consumption, and hourly weather does not resolve intra-hour appliance peaks.

A separate five-second monitor checks fresh SOC, grid and battery power. Automatic home-battery charging is reduced from 6 kW down to the available headroom under the **16 kW** total consumption ceiling (household including Tesla plus home-battery charging, without crediting PV or discharge), using an owned hold when no charging power remains. Required Tesla charging keeps its stable **16 A three-phase** setpoint, approximately **11.04 kW** at 230 V, subject to verified charger/cable limits. Ordinary household fluctuations change the home-battery setpoint rather than restarting the Tesla. If essential loads plus Tesla still exceed the ceiling after home-battery charging reaches zero, site safety can stop the Tesla. This polling cannot guarantee an instantaneous hard ceiling against sudden uncontrollable loads. Manual actions retain their existing start-only grid check.

After an automatic charge target is reached, the controller immediately switches to a **hold** without releasing normal mode in between. Its discharge limit is zero and its charge limit remains 6 kW, so surplus solar may still charge the battery without forcing grid charging. The planner also holds when the battery already has sufficient energy, including after restart, and during 23:00–23:05 and 12:00–12:05 opening buffers. Grid charging and the battery hold both end by **06:55/16:55**. Normal inverter operation resumes during the final five-minute low-tariff buffer, whose modeled demand and solar are included in the energy target. Manual override and grid safety can release the automatic hold earlier.

`POST /inverter/automation-hold` uses the same stable owner and finite expiry as charging. `capabilities.automationHold` is required before automatic charging is enabled; an older controller cannot silently fall back to discharging after its target. `control.automationMode` distinguishes `charge` and `hold`; a hold reports setpoint zero, not measured zero power. `/api/status.automation` adds `holding` and `holdUntil`. The dashboard displays « batterie en réserve jusqu’à… ». Fifteen-minute renewals keep the hold alive; the cutoff lease includes the controller's five-second cleanup margin so normal operation resumes at the requested wall time. Process/device failure retains the finite inverter fallback and cannot guarantee preserved energy through an outage.

Controller automation commands use a stable owner and finite leases of at most 16 minutes. A new controller capability is required; older controllers block automation. Charging may continue until exactly **06:55:00/16:55:00**, unless its SOC target or a safety condition stops it sooner. The final lease expires five seconds later so the controller's cleanup starts at the requested cutoff, without subtracting fallback or network margins from useful charging time. Its inverter fallback still bounds control if a process stalls or dies. Shutdown conditionally stops any possibly issued owned command, including an ambiguous activation still in progress. An owner stop cannot stop another owner's or a manual session.

The runner renews intermediate leases 30 seconds before expiry while retaining their charge or hold mode. The planner, charge breakdown and battery projection count charging through the full window. Both the controller and orchestrator retain an unacknowledged cutoff stop and retry it every five seconds after a failed attempt, without overlapping requests or issuing a new charge after cutoff. Retries can proceed when ordinary status is unavailable, but must preserve any confirmed manual or foreign replacement. A successfully released automatic expiry can recover after a fresh safe controller read; actual device faults remain blocked.

A manual command pauses automation persistently, including after its SOC target is reached; **Mode auto** resumes it after the controller acknowledges normal operation. `data/automation.json` stores the stable lease owner and override via private atomic writes, separately from measured quarter-hour history; `AUTOMATION_STATE_PATH` can override the path. A corrupt file is retained and blocks automatic control instead of resetting ownership. Keep this local automation-state file alongside the service and include it in backups; PostgreSQL history does not replace it. Run one orchestrator per automation-state file and history database.

Build with `pnpm --filter energy-orchestrator build`, then run `pnpm start:energy-orchestrator`. Output lives in `services/energy-orchestrator/dist/`. SIGINT and SIGTERM stop the HTTP server.


## Wattpilot in the orchestrator

The orchestrator uses the existing `ENERGY_CONTROLLER_URL`, with no new credential or device connection. The controller alone holds the local Wattpilot password. Status and controls share a bounded, pending-deduplicated HTTP reader with a short cache; read requests never issue commands. Background battery-estimation reads skip charger polling.

`GET /api/status` and `/api/planner` include `wattpilot` telemetry and `integrations.wattpilot`. `GET /api/controls` includes `car` controls: `available`, `canPause`, mode, per-phase `currentAmps`, configured `phaseMode` and `phaseSwitchingSupported`, actual measured `powerKw`, vehicle presence and effective current limits. Appareils displays the live connection/mode independently of GEN24 and Tesla. Accueil shows measured charger power; its connector animates toward the car only with fresh nonzero power. Unknown/stale power stays unknown and leaves Maison inclusive of car load.

`POST /api/controls/car` accepts `{"mode":"normal","currentAmps":6,"phases":1}`, `{"mode":"eco","currentAmps":6,"phases":3}` or `{"mode":"pause"}`. The phase field is optional for normal/eco and restricted to integers 1 or 3; omission preserves the current device setting. Pause accepts no current or phase fields. An explicit phase choice requires verified device support and the response must confirm that configured selection. Existing same-origin, JSON and body-size protections apply. Old car power/SOC payloads are rejected; `{ "mode":"auto" }` explicitly enables the automatic policy. Normal and eco are manual device modes; eco depends on the device configuration and does not establish solar-only operation. Commands are never automatically replayed; unconfirmed results report `outcome: "unknown"`.

Battery and car starts share a mutation lock and require fresh site measurements. Headroom reserves three phases at 253 V per phase without assuming the car's actual phase count, credits measured car load only when its timestamp is within three seconds of the site reading, and protects against a later loss of home-battery discharge. Car starts also reserve a fresh active battery charge target minus the battery charge already measured, so a battery ramp cannot hide future demand. Positive battery charging additionally reserves the difference between the connected car's configured current demand and its actual power while it ramps or waits. An unconfigured/paused/unplugged charger adds no reservation; an unknown configured charger blocks new battery charging. Phase selection is not a physical relay observation, so both checks retain the conservative three-phase reservation even when one phase is requested. These are command-time checks, not continuous load regulation.

The controller now supervises owned software leases independently of the orchestrator and retries unconfirmed cleanup. A killed/unreachable controller or failed host still cannot guarantee physical pause because no device-side expiry is verified. Car-separated measured history and a generalized optimizer remain future work.

## Automatic Tesla charging

The first deployment starts in **manual** car mode. In **Pilotage**, **Mode auto** pauses the current manual charger setting, establishes a supervised controller session and persists opt-in. Manual **Charger**, **Mode éco** and **Pause** persist manual mode; external conflicting settings also relinquish automatic ownership. GET status/planner/control reads never enable, wake or actuate anything.

The active policy distinguishes three cases in `Europe/Zurich`:

- **Night, 23:05–06:55:** force Normal only while fresh Tesla SOC is below the coming morning's minimum:60% Monday/Thursday/Saturday/Sunday,50% Tuesday/Wednesday/Friday. The checkpoint is 06:55. A higher or earlier one-off morning target applies only to this night requirement.
- **Afternoon, 12:05–16:55:** force Normal only below 30%, stopping the forced top-up at 30%. The weekly morning floor and its override do not become an afternoon target.
- **Otherwise:** select **Wattpilot Eco**, including after a minimum is met, during the opening/closing buffers and when SOC is asleep, stale or unknown. Unknown SOC cannot establish that a target was met. No forecast or measured surplus triggers a separate forced daytime-solar charge.

Eco follows the charger's own settings. It is not a claim of exclusive solar supply or zero grid/storage use. Auto's mode is displayed separately from the vehicle's actual charging state, so an idle Eco session is not shown as an active forced charge. Required energy and finish estimates use75 kWh usable car capacity and90% AC charging efficiency; only a valid original Tesla SOC confirms completion. Lower vehicle charge limits, absent car, invalid site state and infeasible deadlines are reported rather than bypassed.

Car demand shares the **16 kW gross-consumption** site budget with home-battery charging. Required Normal charging keeps the Tesla at **16 A on three phases**, approximately **11.04 kW** at 230 V, subject to verified charger/cable limits. Home-battery grid charging receives the remaining headroom from **0 to 6 kW** and yields first as household demand rises. The Tesla current is not adjusted for ordinary load fluctuations. A safety stop remains available when household demand plus Tesla cannot fit even with home-battery grid charging at zero. The orchestrator never takes ownership of manual/foreign battery control; controller-local safety can still curtail its charging power. Site checks retain a conservative three-phase bound because configured phase selection is not physical relay feedback.

### Solar-origin home-battery support at night

The car may use home storage at night **only from a conservatively measured and persisted solar-origin balance**, above the energy protected for the next07:00–12:00 expensive period. Grid-charged, initial and otherwise unknown stored energy are never eligible. The balance starts at zero/unknown; it does not classify an already charged pack as solar energy.

The provenance ledger credits only observed battery charging attributable to solar: measured battery charge minus **total grid import**, bounded by observed PV presence. It does not subtract household AC load from PV DC to prove origin. All battery discharge consumes the solar balance first, regardless of the load served. Unknown gaps, restart intervals and clock/measurement failures debit or invalidate credit conservatively using bounded discharge; unexplained positive SOC changes do not create solar credit. Valid actual SOC also clamps the balance. The ledger is checkpointed alongside existing PostgreSQL history, without a new dependency or history table.

The protected amount reuses the chronological household/PV requirement for07:00–12:00, plus the effective reserve and configured forecast cushion. Later solar cannot erase an earlier morning deficit. Eligible car assistance is bounded by both proven solar storage and stored energy above that protection, with a guard. Unknown provenance or reserve gives **no assistance budget**, while required grid charging and an owned hold remain available when their own safety checks pass.

During assistance, the GEN24 receives an owned **supply window**: charging is blocked and discharge is permitted only up to a cap and a supervised SOC floor. It is not a forced negative-power command. Reaching the floor, losing safe inputs or exhausting the budget transitions to hold. Energy charged from the grid cannot be added to the solar balance and cycled into the car. Planification separately shows the eligible solar-storage budget and next expensive-period protection; unavailable values are **—**, not invented zeroes. A measured zero eligible balance is shown as zero.

### Supervision and planning

The background runner checks current inputs every five seconds and uses software leases of90 seconds by default, renewed without repeating charger setpoints. Forced Normal activations never extend beyond their night/afternoon cutoff or an earlier morning departure. Eco is a distinct supervised mode; changing to it is not a promise that physical power has already stopped. Controller cleanup persists across disconnect/restart and does not replay an old activation. The controller must stay online for software expiry to run; a killed/unreachable controller or failed host is not covered by a verified hardware watchdog.

When an explicitly enabled forced-charge requirement needs fresh SOC from a plugged-in sleeping Tesla, the runner may make one Owner API wake request, poll within60 seconds and fetch original charge_state. The wake cooldown is15 minutes. Cancellation, unplug, changed authority or cutoff aborts polling; denied/auth/rate-limited access does not authorize a blind forced charge. Default Eco does not itself require waking Tesla merely to obtain SOC. Existing Owner credentials and scopes are preserved, following the bounded pattern in [TeslaPy's Owner endpoints](https://github.com/tdorssers/TeslaPy/blob/master/teslapy/endpoints.json) and [wake implementation](https://github.com/tdorssers/TeslaPy/blob/master/teslapy/__init__.py).

Planification shows the active morning or30% afternoon minimum, fresh SOC, required AC energy, forced-charge source allocation, current/phases and any feasible finish or uncovered requirement. Native Eco has no guaranteed solar/grid split or completion promise. Battery projections receive the same date-clipped forced car allocation, including hold or bounded solar-supply intervals; household forecasts remain `excludesCar:true` and measured household history excludes actual car load. Inactive/manual Auto adds no automatic commitment. Unknown mandatory demand is not fabricated as zero, and uncontrolled native Eco demand is not presented as a scheduled forced load.

Settings are listed under `CAR_AUTOMATION_*` in `.env.example`; no new enable flag bypasses durable UI opt-in. `POST /api/controls/car-target` accepts a canonical future `{ "deadline":"...Z", "targetSocPercent":70 }` for the upcoming morning, at least its weekly floor and no later than07:00, or JSONnull to clear it. It preserves current manual/Auto choice and never raises the afternoon 30% floor. No general trip calendar or target editor is added. State and checkpoint files are private under the service data directory.

The night authorization is anchored to the continuously observed23:00 pre-charge solar/stored balances and debited by **all** night discharge, losses and unknown intervals. Its gross cap is `max(0, min(solarAtNightStart, storedAtNightStart - protectedNextHigh) - guard)`. Night grid deposits cannot free initially protected solar or replenish a spent allowance. A late first start or missing or invalid night checkpoint authorizes zero support for that night. The current SOC floor is anchored to current measured energy, so an unexplained positive SOC jump cannot be borrowed as extra solar.

Every supply request additionally carries a fresh inverter `automationFence` (boot UUID and control generation). A delayed old request cannot reopen a spent floor after hold, grid charging, manual takeover, expiry or process restart. The controller consumes that fence before applying the permitted window.


## Daily history browser

**Données** (`/donnees`) shows a chart and one comparison table for a single selected Zurich date. The table offers **15 minutes** and **Par heure** views. Solaire, Maison, Voiture and Batterie each offer Prévu and Mesuré. Energy is shown in whole Wh and battery SOC in percent. All eight columns are initially selected and the choice is remembered locally. The date and hourly aggregation can be shared in the URL (`?date=YYYY-MM-DD&view=hour`). Old `?step=1` links open the quarter-hour view. Coverage and observation details appear in cell tooltips.

Energy is summed within each displayed period and shown as Wh rounded to whole units, preserving partial subtotals and real zero without filling gaps. The table shows each period as a range, such as 10:15–10:30 or 10:00–11:00 in the hourly view. Chart timestamps label the end of each period: 10:30 pairs the preceding quarter's energy deltas with the latest SOC sampled before 10:30 and the SOC prediction for 10:30. All chart series share that horizontal position; actual sample timestamps remain in observation tooltips. The last period ends at 24:00 on the selected day. Tooltips report measured coverage and forecast-quarter counts so partial historical totals remain identifiable. Quarter-hour battery SOC compares the selected pre-target sample with the prediction for the quarter-end target, and its tooltip shows the real sample time. Hourly battery columns and chart lines use the last available observation or prediction inside each hour, without averaging or carrying values across gaps. Solar, house, car and battery estimates come from their saved quarter-hour rows. Each forecast loop replaces future targets atomically; started energy targets stay frozen. New solar rows preserve each independently calculated target; older equal-quarter rows keep their original historical values.

The calendar uses Europe/Zurich internally, including 23/24/25-hour days. Timezone labels and offsets are omitted; repeated clock times use (1)/(2). Full days contain 92/96/100 quarter-hour rows or 23/24/25 hourly rows. Missing values show — and measured zero stays 0. Old hourly aggregates are not divided into invented quarter measurements.

The page fetches one historical-day response for the selected date and reuses it for the chart, view switches and column changes. Afficher/Réessayer refreshes cached data. Older requests are cancelled. No live hardware, control or weather request and no periodic history poll is added.

### Separate household and car energy

The domain tables have one scope each:

| Domain | Observations (Wh) | Forecasts (kWh) |
| --- | --- | --- |
| House, excluding charging | `house_observations` | `house_forecasts` |
| Car charging | `car_observations` | `car_forecasts` |
| Solar production | `solar_observations` | `solar_forecasts` |

The 30-second collector reads the authenticated Wattpilot cumulative AC counter alongside GEN24. It subtracts charging before writing `house_observations`; there is no archived combined house/car channel. Charging is recorded independently when GEN24 is unavailable. For house subtraction, both counter pairs must be within 30 seconds, using real timestamps and the latest valid pair before each UTC quarter boundary. This is bounded approximate alignment, not exact simultaneous metering. Native component resets, identity changes, missed quarters and negative net deltas leave gaps or establish new baselines. No SOC conversion or assumed zero charging fills missing data.

House, car, solar and battery observations and finalized counter checkpoints commit atomically. Daily totals, history and learning all read the same `house_observations` rows. APIs expose house and car separately, with `householdIncludesCar: false`; they contain no `totalHousehold` field. Retained readings remain partial subtotals without inferred duration coverage. Original hardware total counters are transient calculation inputs, not persisted energy observations.

The `household-profile-v3-car-free` model uses scope `household_excluding_car`, `excludesCar: true`, and learns or averages only `house_observations`. Incompatible models are ignored. Configured car-free fallback values supply missing predictions while measured history accumulates. House forecast rows need no per-row car inclusion flag because their scope is always house-only.

### Car forecast history

`energy_history.car_forecasts` stores charging predictions, with exactly `interval_start` (a UTC quarter-hour boundary) and `energy_kwh` (finite, nonnegative AC charging energy). The scheduled forecast publisher integrates the exact overlap of automatic charging slots with each quarter; short sessions are not rounded up to full quarters. An available automatic allocation records zero for quarters outside its slots. Missing, invalid, unavailable, inactive/manual and unallocated native Eco forecasts remain absent rather than being represented as zero demand.

Car forecasts commit with solar, house, battery and batch metadata. Started quarters are immutable, including after restart; only later quarters are replaced, and completed quarters are never generated retroactively. Losing a forecast clears obsolete future rows while preserving started history. No charging plan or per-slot energy is retained in `forecast_batch_v1` metadata. Runtime automation continues to calculate its current allocation in memory.

Forecast GETs return `carEstimates` from these rows instead of the old saved `carCharging` plan. `/api/history/day` returns the same quarter energy points as `{ start, end, estimatedChargingKwh }`; Données compares them with `car_observations` in its table and chart. Neither endpoint recalculates charging predictions or sends charger commands.

### Initial household learning

An empty car-free model retries at eligible quarter-hour batches with the existing fifteen-minute backoff, rather than waiting for the next midnight. Once observations are available, ordinary daily model reuse resumes. The learning page reports an empty model as waiting for measurements, and shows its next eligible training time.
